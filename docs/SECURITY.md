# Security model

Target: OWASP ASVS 4.0.3 Level 2. No codebase can promise zero vulnerabilities; these controls, the tests that prove them, independent review and a penetration test before each market goes live are how we keep the risk low.

## Threats we design against

| Threat                            | Control                                                                                                                                                                                                                                                         | Where                                                                |
| --------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| Credential stuffing / brute force | Argon2id hashing; per-IP, per-account and per-target limits in Redis shared by all instances; progressive lockout (1, 5, 15, 60 min) with an email to the owner; breached-password check (k-anonymity)                                                          | `modules/auth/flows/login.service.ts`, `infrastructure/rate-limit/*` |
| Account enumeration               | Signup, resend and reset always return the same response; a wrong email burns the same Argon2 time as a wrong password; a locked account answers "invalid credentials"                                                                                          | `signup.service.ts`, `login.service.ts`, `password.service.ts`       |
| Code guessing                     | 8-digit codes, keyed-hash stored, 5 attempts per code then dead, 15-minute expiry, per-account limit                                                                                                                                                            | `codes/verification-code.service.ts`                                 |
| Stolen access token               | 10-minute JWT bound to a session id; every request checks the session is live (Redis, DB fallback), so logout, password reset or theft detection stops it immediately                                                                                           | `common/auth/access.guard.ts`, `sessions/session.service.ts`         |
| Stolen refresh token              | `HttpOnly; SameSite=Strict; Path=/v1/auth` cookie; rotated on every use; replaying an old one revokes every session for the user and emails them; a 15-second grace covers two tabs refreshing at once                                                          | `sessions/rotation.policy.ts`                                        |
| CSRF on cookie endpoints          | SameSite=Strict plus an exact Origin check on refresh and logout; everything else uses bearer tokens                                                                                                                                                            | `common/auth/trusted-origin.guard.ts`                                |
| Privileged account takeover       | TOTP is mandatory for every non-vendor role; until enrolled, the session can only enrol; TOTP codes cannot be replayed; recovery codes are single-use; challenge tokens are single-use and expire in 5 minutes                                                  | `access.guard.ts`, `mfa/*`                                           |
| Broken access control / IDOR      | Deny by default (`@Public()` opt-out); permissions are compiled from the shared registry; forbidden admin routes answer 404; tenant-scoped queries return 404 for other tenants                                                                                 | `access.guard.ts`, `files.service.ts`, `countries.controller.ts`     |
| Malicious uploads                 | Private bucket; presigned PUT pinned to type and exact length; server reads the first bytes and rejects anything whose real type differs (the object is deleted); downloads are 5-minute signed links with `attachment` disposition; every view is audit-logged | `modules/files/*`                                                    |
| Sensitive data at rest            | AES-256-GCM field encryption with versioned keys and per-field context (AAD); keyed hashes for lookups; MFA secrets encrypted                                                                                                                                   | `infrastructure/crypto/*`                                            |
| Tampering with history            | Audit log is append-only by database trigger (update, delete and truncate are refused) and hash-chained, so any edit made by someone with direct database access breaks the chain                                                                               | `migrations/0001_audit_integrity.sql`                                |
| Injection                         | Prisma parameterised queries only (raw SQL only through tagged templates); Zod validation on every input; JSON bodies capped at 100 KB                                                                                                                          | controllers, `bootstrap.ts`                                          |
| XSS / clickjacking                | Nonce-based CSP with `strict-dynamic`, no inline script; `frame-ancestors 'none'`; React escapes all text; the API serves `default-src 'none'`                                                                                                                  | `global-fulfilment-web/src/middleware.ts`, `bootstrap.ts`            |
| Information disclosure            | One error shape with stable codes; 5xx bodies never include internals; logs redact passwords, codes, tokens, cookies and auth headers                                                                                                                           | `all-exceptions.filter.ts`, `app.module.ts`                          |
| Misconfiguration                  | The API refuses to boot with missing or placeholder secrets, a log-only email transport in production, or a non-HTTPS public URL                                                                                                                                | `config/config.schema.ts`                                            |

## Phase 1 controls (onboarding)

| Area            | Control                                                                                                                                                                                                     |
| --------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Identity data   | Verification answers (names, addresses, phone numbers) and ID numbers are encrypted with AES-256-GCM, each bound to the vendor by its encryption context; only the last four ID digits are stored in clear  |
| Least privilege | Readers (`verifications.read`) see the case; only reviewers (`verifications.review`: compliance, super admin) open documents or reveal the full ID number, and every such view is audit-logged              |
| Country scoping | Country operations staff only ever see verifications for their own country; other countries answer 404                                                                                                      |
| Vendor roles    | Only the vendor owner can verify, accept agreements, manage the team and set markets; members can read                                                                                                      |
| State machine   | Answers are locked once submitted; only submitted cases can be decided, once; vendors activate only when approved and the latest vendor agreement is accepted                                               |
| Documents       | Draft and submission check every referenced file belongs to the vendor, is a KYC document and passed the content check                                                                                      |
| Legal records   | Published versions and acceptances are append-only in the database; accepting an outdated version is refused                                                                                                |
| Invitations     | 256-bit single-use tokens stored as keyed hashes, sent in the URL fragment, 7-day expiry, a new invite revokes the old one, per-vendor daily cap; removing a member suspends them and revokes every session |

## Phase 2 controls (stock)

| Area             | Control                                                                                                                                                                                                                     |
| ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Country scoping  | Warehouse operators and country operations staff only see warehouses, shipments and stock in their own country; anything else answers 404                                                                                   |
| Vendor isolation | Products, shipments, stock, labels and custody history are always filtered by the caller's vendor; product images must be the vendor's own uploads                                                                          |
| Trading gate     | Adding products or sending stock needs an active vendor that has accepted the current vendor agreement                                                                                                                      |
| Evidence         | Receiving needs at least one shipment photo, plus photos of any damage; photos must be uploaded by the operator doing the count, can be used once, and can never be changed or removed                                      |
| File purposes    | Each upload purpose has its own upload and view permission (vendors can't upload warehouse evidence, operators can't upload identity documents)                                                                             |
| State machine    | One shared lifecycle decides which action is allowed from which status; every change locks the shipment row, so double receiving or receive-versus-cancel can't both win                                                    |
| Stock history    | Every quantity change is written to an append-only movement log, and every receipt, put-away and move to a hash-chained custody record that refuses edits and deletes                                                       |
| Staff            | Only super admins invite staff; a super admin can't be invited or suspended through the console; invitations are single-use keyed-hash tokens that expire in 3 days; new staff must set up two-factor before using anything |

## Phase 3 controls (money)

| Area                 | Control                                                                                                                                                                                                                                                                                                 |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Ledger integrity     | Ledger entries can't be changed or deleted; a database trigger locks the wallet, checks each entry follows the previous balance and has the right sign for its type, and applies it; wallets refuse direct balance changes and deletes; a nightly job compares every balance with the sum of its ledger |
| Double posting       | Each posting carries an idempotency key unique per wallet (top-up, onboarding, hold, storage run, adjustment), checked under the wallet lock                                                                                                                                                            |
| Webhooks             | One endpoint per country account; the Stripe signature is checked on the raw body with a 5-minute tolerance; each event is stored and processed in one transaction, keyed by provider, account and event id, so replays are ignored                                                                     |
| Crediting            | A top-up is credited only when the session, account, country, currency and gross amount all match what we created; mismatches are audited and never credited                                                                                                                                            |
| Refunds and disputes | Taken back in proportion to what reached the wallet, including while the wallet is paused; any shortfall pauses the wallet; a refund or dispute for a payment not yet confirmed is refused with 503 so Stripe sends it again later                                                                      |
| Maker-checker        | Price changes and adjustments above the market's limit need a different person to approve, enforced in the service and by database checks; one person's adjustments are capped per day under an advisory lock                                                                                           |
| Tenant scoping       | Vendor wallet routes only ever use the caller's vendor; country staff see only their own market's prices; vendors never see internal approval limits                                                                                                                                                    |
| Test mode            | The sandbox processor and its pay route are refused in production, and production refuses test Stripe keys                                                                                                                                                                                              |
| Checkout redirect    | The web app only follows a checkout link to its own origin or `checkout.stripe.com`                                                                                                                                                                                                                     |

## Independent review of Phase 3 — 25 Oct 2026

| #   | Severity | Finding                                                                                     | Fix                                                                           |
| --- | -------- | ------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| 1   | High     | A lost dispute (or any refund) on a paused wallet failed, so the money was never taken back | Card payment reversals post even while a wallet is paused                     |
| 2   | Medium   | Winning a dispute paused the wallet again                                                   | Only an opened dispute pauses; a win is audited and left to finance           |
| 3   | Medium   | A lost dispute after a partial refund took back too little                                  | Dispute amounts are added to what was already refunded                        |
| 4   | Medium   | A refund arriving before its payment confirmation was dropped for good                      | Refused with 503 and not stored, so Stripe retries it after the payment lands |
| 5   | Medium   | Event dedupe ignored which country account received it                                      | Dedupe is per provider, account and event                                     |
| 6   | Medium   | Two shipments submitted at once could both get the free first-shipment stocking             | The wallet is locked before checking                                          |
| 7   | Low      | A cancelled shipment used up the free stocking                                              | Cancelled shipments don't count                                               |
| 8   | Low      | Country staff could read other markets' price history                                       | Scoped to their own market                                                    |
| 9   | Low      | Vendors could see internal adjustment limits                                                | Removed from the vendor view                                                  |
| 10  | Low      | Top-up presets were wrong for currencies without minor units                                | Scaled by the currency's minor units                                          |

The browser check also showed the 10-a-minute limit on session refresh would sign out people sharing one office network; refresh is now limited to 60 a minute per address (it still needs a valid, rotating refresh cookie).

## Phase 4 controls (orders and shipping)

| Area             | Control                                                                                                                                                                                                                                                                                                                                                        |
| ---------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Tenant scoping   | Vendor routes always filter by the caller's vendor; warehouse staff only see orders from their own country; API keys act only for their own vendor                                                                                                                                                                                                             |
| Status machine   | One shared table of allowed moves, enforced in the services and again by a database trigger; ownership, origin, destination and currency can't change after creation; orders can't be deleted and their timeline is append-only                                                                                                                                |
| Stock            | Lots are locked in a fixed order while reserving; reservations, shipping and releases are written to the movement log and custody chain                                                                                                                                                                                                                        |
| Packing          | The server counts scans per line and refuses to record a pack until every unit is scanned                                                                                                                                                                                                                                                                      |
| Money            | The fulfilment fee is taken in the same transaction as the order; shipping is taken when the label is bought, under the order lock with one Redis lock per label purchase; a definite carrier refusal refunds the charge, an unconfirmed result keeps it and the retry looks for an existing label first; labels that can't be recorded are voided and audited |
| Cancellation     | Releases stock, returns everything charged for the order (worked out from the ledger), voids any label; only country operations and admins decide requests                                                                                                                                                                                                     |
| Carrier webhooks | One endpoint per country account with a long random token in the path, compared in constant time and masked in logs; the payload only names the parcel — status is always re-fetched from the carrier; replays are ignored and failed fetches are answered 502 so the carrier retries                                                                          |
| Personal data    | Recipient details are encrypted at rest; staff who neither pack nor cancel orders see them masked; public tracking shows only city, country and carrier events                                                                                                                                                                                                 |
| Integration API  | Keys are 256-bit secrets stored as SHA-256 hashes, compared in constant time, shown once, capped at 10 per vendor, revocable, refused for vendors that aren't active, never logged, and rate-limited per key                                                                                                                                                   |
| Imports          | 250 KB and 1,000 rows per file, 300 orders per file, 2,000 a day, one import at a time per vendor                                                                                                                                                                                                                                                              |

## Phase 5 controls (fulfilment partners)

| Area            | Control                                                                                                                                                                                                                                                                                                                                              |
| --------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Tenant scoping  | Partner users carry their partner in the session; every warehouse, location, inbound, lot, custody and order query for them is limited to their own partner's warehouses, and anything else answers 404. Country operations only see partners in their country                                                                                       |
| Operating gate  | Warehouse permissions work only while the partner is active — checked on every request, so suspension takes effect immediately; profile, team and earnings stay readable                                                                                                                                                                             |
| Least privilege | Partner roles have no vendor, finance, price, staff or platform permissions. Partner staff can't see bank details, deposits, evidence, the team or earnings. Only partner managers create partners, assign warehouses and activate, reinstate, offboard or terminate                                                                                 |
| Four eyes       | The database refuses a check or insurance review by the person who submitted it, a deposit confirmation or release by the person who recorded it, bank-detail verification by the person who entered them, and a payout approval by the person who requested it                                                                                      |
| Evidence        | Partners can only attach files they uploaded as partner evidence; reviewers can only open files linked to that partner's checks or policies, and every view is audited                                                                                                                                                                               |
| Bank details    | Encrypted with AES-256-GCM bound to the partner; shown masked; a change resets verification and emails the partner; full details are shown to finance only on request, and every view is audited                                                                                                                                                     |
| Money           | The partner ledger is append-only, idempotent per event and can't go negative (database trigger under the partner lock); payouts are capped at the available balance and refused if the bank details changed after the request; holdbacks stay held while a partner is suspended or offboarding; partners can't record more boxes than were declared |
| Lifecycle       | One shared table of allowed status moves, enforced in the services and by a database trigger; the country can't change; partners can't be deleted; warehouses and users must be in the partner's country; closing a partnership suspends every account, revokes sessions and cancels invitations                                                     |
| Agreements      | Vendors are only offered and can only accept vendor documents; partners only partner documents, and only the current version                                                                                                                                                                                                                         |

## Partner verification and trust controls (homepage and partner brief)

| Area           | Control                                                                                                                                                                                                                                                                                                                                                                                               |
| -------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Data kept      | Identity is checked by Stripe Identity; we keep only the status, the provider's reference and the time, never ID numbers or images. Bank details stay with Stripe Connect; we keep a masked summary and a fingerprint. Tax references are encrypted. Proof of address is deleted once the retention period after the decision passes, and closed applications' proof and space photos are deleted too |
| Verification   | Every step is server-checked: proof of address must be from the last 92 days and the reviewer must confirm it matches the storage address; changing the name or address reopens identity, proof of address and the space, and invalidates the signature; Stripe's verified name must match the application                                                                                            |
| Separation     | The person who reviews the steps can't approve the partner; payouts are approved by someone other than the requester; a test order is assessed by someone other than the person who placed it; stock counts are resolved by staff, not the partner                                                                                                                                                    |
| Stock limits   | Each tier caps the total stock value and the value of any one item. Checked when a vendor submits an inbound and again when a partner receives it; partners can't record more boxes or units than were declared                                                                                                                                                                                       |
| Pay            | A partner is paid for an order only once a dispatch photo and tracking exist; photos can't be reused from receiving or other orders. 20% of each earning is held for 60 days, and stays held while the partner is paused, closing or ended, or has an unresolved flagged or missed count, or a failed test order in the last 90 days                                                                  |
| Payouts        | Sent through Stripe Connect with an idempotency key; refused if bank details changed after the request, re-checked before every send attempt, retried automatically for 20 hours and then left for manual settlement. A bank change (including removal) is recorded and emailed                                                                                                                       |
| Blind counts   | Partners don't see expected quantities, and lots under an open count are hidden from their stock and custody views. Each count needs a new video                                                                                                                                                                                                                                                      |
| Test orders    | Only a vendor flagged in the database as an internal test account can be the test vendor; partners can't see test order results on their scorecard                                                                                                                                                                                                                                                    |
| Partner powers | Partners can hold an inbound with a reason but can't add charges, refuse it or send it back; the platform's operations team does that. They never see what vendors pay                                                                                                                                                                                                                                |
| Tiers          | Raised automatically by the daily job when the scorecard qualifies; a manual change by a partner manager holds the tier for 90 days                                                                                                                                                                                                                                                                   |

## Phase 6 controls (custody and trust)

| Area                | Control                                                                                                                                                                                                                                                                                                                                                                                 |
| ------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Claims              | One person opens or assesses a claim, a different person decides it (database constraint plus a service check); the person who opened a claim can't assess it. Assessing needs `claims.assess`, deciding needs `claims.decide` (finance or super admin). Country ops only see their country                                                                                             |
| Settlement          | One transaction: optional write-off with a ledger movement and custody event, a wallet credit with a per-claim idempotency key, recovery from the partner's available balance (never the held bucket) and then from confirmed deposits through append-only draws. A database constraint makes the split add up to the compensation. Compensation can't exceed the declared value        |
| What each side sees | Vendors never see partner names, partner responses or recovery amounts; partners never see vendor names or claims still being looked into; evidence files and our own cover are staff only. Partners respond once                                                                                                                                                                       |
| Vendor reports      | Only on the vendor's own sent orders or held stock, for no more units than exist, with attachments the vendor uploaded; one live claim per order or lot; rate limited per vendor                                                                                                                                                                                                        |
| Holdback            | Released only when the partner has no open or assessed claims, as well as the earlier conditions                                                                                                                                                                                                                                                                                        |
| Transfers           | Requested by country ops within one country, only for free stock that isn't already moving, and only to hubs with room under their tier (stock on the way counts). The sender must add a seal number, carrier, tracking and their own photos; the receiver counts blind, can't be the dispatcher and can't record more than was sent. Anything short becomes a claim against the sender |
| Paused hubs         | Counts and transfers use a permission that still works while a hub is paused or closing, so stock can be counted and moved out; all other warehouse work stays blocked                                                                                                                                                                                                                  |
| Alerts              | Daily checks raise one open alert per subject: parcels with no carrier scan after the country's limit, counts that came up short, loss rates over the country's limit, and low trust                                                                                                                                                                                                    |
| Trust               | A score out of 100 from dispatch evidence, count accuracy, uncleared counts, failed test orders, partner-liable claims, losses and missing scans. Below the country's floor the hub is paused automatically, an alert is raised and a full count requested; tier raises need the promotion score. Suspending or closing a hub also requests a full count                                |
| High value          | Parcels at or above the country's value need a tamper seal number before hand-off                                                                                                                                                                                                                                                                                                       |
| Audit chain         | The latest audit hash is written once a day to object storage with a write-if-absent request; in production that bucket should have object lock enabled                                                                                                                                                                                                                                 |

## Phase 7 controls (storefronts and buyers)

| Area                | Control                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| ------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Prices              | The server prices every quote and checkout from the listed price, the vendor's own discount code, the carrier rate and the country's tax rules. Nothing the buyer sends is trusted except product ids, quantities, the address and the code. Database constraints make the total and the vendor/platform split add up                                                                                                                                                                                |
| Payment             | An order is marked paid only by a verified payment event whose amount, currency and checkout reference match the order; anything else is audited and the money is refunded to the buyer automatically, as is a second payment for an order that's already paid. Paying twice, or a late event after expiry, changes nothing. The practice payment page only works with the practice processor and never in production                                                                                |
| Vendor money        | The buyer's payment is held for the vendor. The return window and the hold start when the parcel leaves the warehouse, so nothing is paid out for an order that hasn't shipped. Their share (less refunds) then goes to their connected bank once the window and the market's minimum hold have passed, never while a return or a card dispute is open, and not for 72 hours after their bank details change. Each payout has an idempotency key                                                     |
| Refunds             | Every refund is a row with its own key, reserved before the card processor is called and settled with the processor's refund id, so a retry or a double click repeats the same refund instead of sending another, and Stripe's own refund notice never adds to it a second time. Never more than is left on the order. A full refund cancels a payout that hasn't gone. Vendors can only refund up to their own share; anything more needs finance (`storefronts.manage`). Country ops can only look |
| Returns             | Only the buyer who paid, only once the order has been sent and before the return window fixed at payment closes, one open return per order (database index). The vendor or finance decides; an accepted return refunds straight away and, if the card refund fails, waits for a retry instead of being lost                                                                                                                                                                                          |
| Discount codes      | Vendor-scoped and unique per vendor. A use is reserved when checkout starts (with a conditional update, so two buyers can't both take the last one) and given back if the checkout lapses or fails                                                                                                                                                                                                                                                                                                   |
| Buyer sign-in       | No passwords. A one-time link with 256 bits of randomness, stored only as a keyed hash, valid for 15 minutes, and any older unused link is cancelled. The response is the same whether or not the email has bought anything. Links arrive in the URL fragment so they never reach server logs, and the page removes them from the address bar                                                                                                                                                        |
| Buyer session       | A random session cookie, stored as a keyed hash, `HttpOnly`, `SameSite=Strict`, sent only to `/v1/buyer`, 30 days, revoked on sign-out. Every change (`link`, `session`, `sign-out`, return requests) also checks the request comes from our web origin                                                                                                                                                                                                                                              |
| What each side sees | The vendor sees the buyer's name and town but not their email or full address, on the store order and on the warehouse order it creates. Buyers never see the vendor's share or ours. The public receipt link shows only the items, totals and status, and stops working after 7 days. Addresses are encrypted at rest                                                                                                                                                                               |
| Rate limits         | Checkout per IP and per buyer email; sign-in links per IP and per email; session starts per IP; public reads throttled                                                                                                                                                                                                                                                                                                                                                                               |
| Checkout redirect   | The web app only follows a payment redirect to our own origin or the card provider's checkout host                                                                                                                                                                                                                                                                                                                                                                                                   |

## Independent review of Phase 7 — 26 Oct 2026

A separate reviewer read the commerce code without seeing our reasoning. Pricing, payment matching, webhook signatures, duplicate events, magic-link tokens, CSRF on the buyer cookie, the checkout redirect allowlist and tenant isolation held up. What it found, and what changed:

## Test sign-in shortcuts

`AUTH_TEST_SHORTCUTS=on` lets a new account skip the emailed code (its password is still checked, rate-limited and audited) and lets staff skip authenticator set-up for one sign-in (the session is marked as passed; the account stays un-enrolled, so it's asked again next time). It's off by default, the endpoints answer 404 when off, and configuration refuses to load with it on when `NODE_ENV=production`. It must be removed before real users or data are on the system.

## In-app helper and support cases

- The helper never reads what people type into forms. It records field labels only ("Went to Tracking number"), the page path, and the error type, status and log reference from failed requests.
- Messages people type to the helper, and every step in the trail, are scrubbed of card-like digit runs in the browser and again on the server. Reports are validated against a strict shape: page paths only (no full URLs or query strings), at most 20 steps, 1,000 characters of message.
- Reporting is rate limited per address (20 an hour) and per signed-in user (30 a day), on top of the route throttle. The anonymous route stores a contact email but never sends mail to it, so it can't be used to send email to strangers.
- The same failure (error type, status, endpoint and page, with ids removed) is grouped into one open case under a database lock, so a widespread outage produces one case and one email to support, not thousands.
- Only staff with `support.read` see cases; resolving needs `support.manage`, is audited, and notifies the people who reported it.

### Helper answers (phase 2)

- Off by default (`ASSISTANT_AI=off`); the answer endpoints return 404 until it's switched on, and configuration refuses to load if it's on without `ANTHROPIC_API_KEY`. The key lives only on the server.
- What is sent to the AI provider per question: the page's written notes, the published guides, FAQs, prices, order and shipment stage meanings, the person's question and the last six chat turns (card-like numbers removed), and, for a signed-in seller, a short summary of their own account: business name, wallet balance and its five latest entries, unfinished stock shipments and counts of open orders. Nothing from another business, no staff data, no addresses, no form values.
- The model is told to answer only from that information, to reply UNSURE otherwise, and to treat the person's words as questions rather than instructions. An UNSURE reply, an error or a timeout is never shown; the person is offered the team instead.
- Every question is logged with its outcome and token counts (question text scrubbed). Limits: 30 an hour per address, 60 a day per user, and `ASSISTANT_DAILY_ANSWERS` across everyone (default 2,000), after which questions go straight to the team.
- Before switching it on: name the AI provider as a processor in the privacy policy for each market, and check the provider's data retention terms.

### Row-level security — deferred

The plan called for PostgreSQL row-level security on partner-visible tables. The API uses Prisma with a pooled connection, so a per-request setting would have to be applied inside every transaction (`SET LOCAL`) and every read wrapped in one, and a single missed wrapper would fail open just like a missed service filter. For now isolation lives in one place (`warehouseScope`) used by every warehouse service, and the partner isolation suite (`test/partners-operations.e2e-spec.ts` and `test/partners-onboarding.e2e-spec.ts`) proves that another partner's warehouse, inbound, stock and orders, and another country, answer 404. Revisit before more than a handful of partners are live: either move partner reads behind a database role with RLS policies keyed on a transaction-local partner id, or route partner traffic through views that apply the filter.

### Residual risks we accept for now

- **Lockout as denial of service.** Repeated wrong passwords from many addresses can still lock an account for up to an hour (the owner is emailed). This is the usual trade-off against password guessing; Phase 1 adds "unlock via email link".
- **Audit chain is unkeyed.** Someone with database-owner rights could rewrite the chain consistently. Mitigation: the app runs with a role that cannot alter triggers, and the latest hash is anchored in object storage daily (enable object lock on that bucket in production).
- **Stale upload objects.** Re-uploads to an already-used `incoming/` key are never served but take up space; set a bucket lifecycle rule to expire `incoming/` after 1 day.
